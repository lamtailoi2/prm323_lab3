## Verified fine

- **Layering/MVVM:** `job_level.dart` is a pure, unit-tested helper in `core/utils`; the model exposes a thin `level` getter; the view only reads model data (same pattern as `role`). No service/Firebase access in the view.
- **Riverpod:** No new providers or state; the badges derive from the already-watched listing. Correct.
- **Tokens-only:** `_DetailBadge` → `AppTag` uses `surfaceVariant`, `AppRadii.smallAll` (8), `AppSpacing`, `bodySmall`; the `Wrap` uses `AppSpacing.s8/s4`. No raw colors/sizes/insets.
- **Shared reuse:** Reuses the existing compact `AppTag` rather than inventing a component; recorded in `design-system.md` and DC-28. Good.
- **Accessibility:** Explicit `Semantics(container, label, excludeSemantics)` gives one clean "Role: …"/"Experience: …" announcement; badges are non-interactive (touch-target rule N/A); meaning is carried by text, not color alone. Existing `meetsGuideline(androidTapTargetGuideline)` still passes at 360/412 dp.
- **Docs consistency:** No current doc still says "five keywords" (only historical Run 7 / P-20 log entries). The eight-keyword quota math is internally consistent (8 backfill + ~120 rotation ≈ 128 of 250; each keyword ≈ every 2 days < 7-day expiry) across `config.ts`, `firebase-setup.md` §13, G-25 and Run 22. DC-28's labels/semantics match the code exactly.
- **Tests/evidence:** Run 22's 174 files / 557 tests / 19 function tests are accurate and reproduce; `config.test.ts` is picked up by `tsc` + `node --test lib/*.test.js`.
